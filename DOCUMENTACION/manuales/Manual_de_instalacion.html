1.Propósito y alcance

Este manual explica cómo instalar y poner en marcha la plataforma web del Plan Vida Abundante (PVA) de la Comunidad Cristiana Manantial de Gracia de Girón. La plataforma reúne dos módulos independientes: Casas de Vida (personas nuevas, reportes de asistencia, seguimiento, ofrendas y reportes) y Escuelas de Formación (procesos de formación, inscripciones, actividades, asistencia y seguimiento).

Está dirigido a quien instale o mantenga la plataforma: el equipo de desarrollo o la persona de la iglesia que se encargue de la parte técnica. Se supone que sabe abrir una terminal y copiar comandos; no hace falta saber programar.

Qué cubre: instalación en un equipo con Windows 10 u 11 para uso local o de pruebas, con la configuración de desarrollo (config.settings.development), que es la que se verificó al escribir este manual.

Qué no cubre: la publicación en un servidor de Internet. El proyecto incluye una configuración de producción (config.settings.production), pero la plataforma no se ha desplegado todavía, así que no se documentan servidor, dominio ni certificado: [Por confirmar: servidor, dominio y procedimiento de despliegue en producción].

2.Componentes del sistema

La plataforma es una aplicación web monolítica: un solo programa en Django sirve las páginas y se conecta a una base de datos PostgreSQL. Las personas la usan desde el navegador del computador o del celular.

ComponenteQué esDónde está en el proyecto
Aplicación webDjango 5.2 sobre Python 3.11ccmg/backend (apps cuentas, pva, formacion, ofrendas, nucleo, publico; configuración en config/settings)
InterfazPlantillas HTML, Bootstrap 5, CSS y JavaScript propiosccmg/frontend/templates y ccmg/frontend/static
Base de datosPostgreSQL 16; el esquema se crea con un script SQL, no con migracionesccmg/backend/base_datos/esquema.sql y datos_iniciales.sql
ConfiguraciónArchivo .env con las credenciales (no se sube al repositorio)Raíz del proyecto; plantilla en .env.example
Correo (opcional)Servidor SMTP para recuperar contraseñasVariables EMAIL_* del .env
Dependencias de PythonDjango, psycopg, python-dotenv, openpyxl (Excel), reportlab (PDF), pillowccmg/backend/requirements.txt
Las tablas de la base de datos las define esquema.sql, incluidas las que Django necesita para sesiones y permisos. Por eso los modelos están marcados como no administrados (managed = False) y no se usa migrate para crear tablas (ver paso 4.5).

4.Instalación paso a paso

Siga los pasos en orden. En cada comando se indica la carpeta donde debe estar la terminal, la terminal que se usa y el resultado esperado. Los ejemplos usan la carpeta C:\Proyectos; puede usar otra.

4.1 Obtener el código

1

Clonar el repositorio

Carpeta: C:\Proyectos · Terminal: PowerShell
git clone https://github.com/JosdaTara/PLATAFORMA-WEB-CCMG-GIRON.git
cd PLATAFORMA-WEB-CCMG-GIRON
Resultado esperado: «Cloning into 'PLATAFORMA-WEB-CCMG-GIRON'… done.» y la terminal queda dentro de la carpeta del proyecto, que contiene ccmg, DOCUMENTACION, .env.example y README.md.

A esta carpeta se le llama en adelante raíz del proyecto.

4.2 Entorno virtual y dependencias

2

Crear el entorno virtual

El entorno virtual guarda las librerías del proyecto aparte de las del sistema. Se crea una sola vez, en la carpeta ccmg.

Carpeta: raíz del proyecto · Terminal: PowerShell
cd ccmg
python -m venv venv
Resultado esperado: no muestra mensajes; aparece la carpeta ccmg\venv.
3

Activar el entorno virtual

Carpeta: ccmg · Terminal: PowerShell
.\venv\Scripts\Activate.ps1
Resultado esperado: el inicio de la línea de la terminal cambia a (venv) PS …\ccmg>.

Si PowerShell responde que «la ejecución de scripts está deshabilitada», ejecute una vez Set-ExecutionPolicy -Scope CurrentUser RemoteSigned, confirme con S y vuelva a activar.

4

Instalar las dependencias

Carpeta: ccmg (con el entorno activado) · Terminal: PowerShell
pip install -r backend\requirements.txt
Resultado esperado: termina con «Successfully installed Django-5.2.18 openpyxl-3.1.5 psycopg-3.3.6 … reportlab-5.1.0» (el orden puede variar) y sin líneas ERROR.

4.3 Variables de entorno

5

Crear el archivo .env

La plataforma lee la conexión a la base de datos y el correo de un archivo .env en la raíz del proyecto. Se crea copiando la plantilla:

Carpeta: raíz del proyecto · Terminal: PowerShell
Copy-Item .env.example .env
notepad .env
Resultado esperado: se abre el Bloc de notas con el archivo .env.

Cambie como mínimo DB_PASSWORD por la contraseña del usuario postgres que definió al instalar PostgreSQL. Si todavía no va a configurar el correo, ponga # al comienzo de las líneas EMAIL_HOST, EMAIL_HOST_USER y EMAIL_HOST_PASSWORD: así los correos se muestran en la terminal del servidor en lugar de intentar enviarse con datos de ejemplo. Guarde y cierre.

La sección 5 explica cada variable.

El archivo .env contiene contraseñas: no lo comparta ni lo suba al repositorio (ya está excluido en .gitignore). Escriba cada línea como NOMBRE=valor, sin espacios antes del nombre ni comillas.

4.4 Base de datos y datos iniciales

6

Crear la base de datos vacía

Carpeta: cualquiera · Terminal: PowerShell
createdb -U postgres CCMG_GIRON
Resultado esperado: pide «Contraseña:» (la de postgres; no se ve al escribirla) y vuelve a la línea de comandos sin mensajes.

El nombre CCMG_GIRON debe coincidir con DB_NAME del .env.

7

Crear las tablas

Carpeta: ccmg\backend · Terminal: PowerShell
$env:PGCLIENTENCODING = "UTF8"
psql -U postgres -d CCMG_GIRON -v ON_ERROR_STOP=1 -f base_datos\esquema.sql
Resultado esperado: tras pedir la contraseña, una lista de líneas CREATE TABLE, CREATE INDEX, ALTER TABLE… que termina sin ninguna línea ERROR.

La primera línea hace que las tildes y la ñ se lean bien; vale para esa ventana de PowerShell.

8

Cargar los datos iniciales (roles)

Carpeta: ccmg\backend · Terminal: PowerShell (la misma ventana del paso 7)
psql -U postgres -d CCMG_GIRON -v ON_ERROR_STOP=1 -f base_datos\datos_iniciales.sql
Resultado esperado: INSERT 0 6. Son los seis roles: Super Administrador, Pastor, Supervisor de Área, Líder de Casa de Vida, Apoyo de Casa de Vida y Coordinador de Formación.

La base queda sin personas, Casas de Vida ni áreas: esos datos los registra la iglesia desde la plataforma o con Importar datos (ver el Manual de usuario).

4.5 Comprobar la configuración y registrar migraciones

9

Revisar que Django se conecta

Carpeta: ccmg\backend (entorno activado) · Terminal: PowerShell
python manage.py check
Resultado esperado: System check identified no issues (0 silenced).
10

Registrar las migraciones de Django (recomendado)

Como las tablas ya las creó esquema.sql, Django cree que tiene 15 migraciones pendientes y lo avisa cada vez que arranca. Este comando las marca como aplicadas sin tocar las tablas:

Carpeta: ccmg\backend (entorno activado) · Terminal: PowerShell
python manage.py migrate --fake
Resultado esperado: una lista de líneas Applying … FAKED. Desde ese momento desaparece el aviso «You have 15 unapplied migration(s)».
Use siempre --fake. Un migrate normal intentaría crear tablas que ya existen y fallaría.

4.6 Crear la primera cuenta de administración

11

Crear el Super Administrador

La plataforma no trae cuentas. La primera se crea desde la terminal; las demás las crea esa cuenta desde Gestión de usuarios.

Carpeta: ccmg\backend (entorno activado) · Terminal: PowerShell interactiva
python manage.py crear_superadmin
Resultado esperado: el comando pregunta, uno por uno, Correo:, Username (opcional, Enter para omitir):, Nombre completo:, Contraseña: y Confirmar contraseña:, y termina con Cuenta Super Administrador creada: admin@iglesia.example (id=1).

Ejemplo ficticio de respuestas: correo admin@iglesia.example, usuario vacío (Enter), nombre «Administrador CCMG». La contraseña debe tener al menos 15 caracteres y no se ve al escribirla; si no cumple las reglas, el comando lo dice y no crea la cuenta.

  • Para crear una cuenta de Pastor desde la terminal existe python manage.py crear_pastor, que hace las mismas preguntas.
  • Para convertir en Super Administrador una cuenta que ya existe: python manage.py crear_superadmin --promover correo@iglesia.example.
Estos comandos leen la contraseña sin mostrarla y necesitan que alguien la escriba en la ventana. No funcionan si se les pasa la contraseña con una tubería o un script.

4.7 Iniciar la plataforma

12

Arrancar el servidor

Carpeta: ccmg\backend (entorno activado) · Terminal: PowerShell
python manage.py runserver
Resultado esperado: «Starting development server at http://127.0.0.1:8000/» y «Quit the server with CTRL-BREAK.» La terminal queda ocupada mientras el servidor esté encendido.

Abra el navegador en http://127.0.0.1:8000. Para apagar el servidor, vuelva a la terminal y pulse Ctrl+C.

Para usar otro puerto, añádalo al final: python manage.py runserver 8080. Para abrir la plataforma desde un celular de la misma red Wi-Fi se necesita runserver 0.0.0.0:8000 y agregar la IP del equipo a ALLOWED_HOSTS en la configuración de desarrollo [Por confirmar: no se probó el acceso desde otros equipos de la red].

8.Entorno de demostración (opcional)

El proyecto trae una demostración con datos ficticios (áreas, una Casa de Vida, personas, reportes y un usuario por rol) para revisar la plataforma sin tocar la base real. Usa su propia base de datos y el puerto 8001, así que puede correr a la vez que la plataforma real.

Carpeta: ccmg\backend (entorno activado) · Terminal: PowerShell
$env:PGCLIENTENCODING = "UTF8"
createdb -U postgres CCMG_GIRON_demo
psql -U postgres -d CCMG_GIRON_demo -v ON_ERROR_STOP=1 -f base_datos\esquema.sql
psql -U postgres -d CCMG_GIRON_demo -v ON_ERROR_STOP=1 -f base_datos\datos_iniciales.sql
python manage.py sembrar_demo --settings=config.settings.demo
python manage.py runserver 8001 --settings=config.settings.demo
Resultado esperado: el servidor de la demostración queda en http://127.0.0.1:8001.

Las cuentas de la demostración usan el dominio demo.test: superadmin@, pastor@, supervisor@, lider@, apoyo@ y coordinador@demo.test. Todas tienen la misma contraseña, definida en la constante CLAVE_DEMO de apps/nucleo/management/commands/sembrar_demo.py.

sembrar_demo se niega a ejecutarse si el nombre de la base no contiene «demo», para no mezclar datos de ejemplo con los reales. Las cuentas de la demostración no sirven en la plataforma real (puerto 8000), ni al revés.

10.Nota de verificación

Verificado ejecutando el sistema

El 24/11/2026 se hizo una instalación limpia en Windows 11 con Python 3.11.9 y PostgreSQL 16, en una carpeta y una base de datos aparte (CCMG_GIRON_manual), siguiendo los pasos de este manual:

  • git clone, creación del entorno virtual e instalación de requirements.txt, sin errores.
  • Creación de la base, esquema.sql sin errores y datos_iniciales.sql con el resultado INSERT 0 6.
  • .env creado a partir de .env.example; manage.py check respondió «System check identified no issues».
  • Creación del primer Super Administrador («Cuenta Super Administrador creada: … (id=1)») y migrate --fake sin errores.
  • runserver: la página pública y el inicio de sesión respondieron con código 200; el inicio de sesión llevó a «Selecciona un módulo» con el rol Super Administrador.
  • Al terminar se apagó el servidor de prueba y se borró la base CCMG_GIRON_manual.

Verificado revisando el código

  • Variables de entorno, valores por defecto y su uso: config/settings/base.py, development.py, demo.py, production.py y .env.example.
  • Preguntas y mensajes de crear_superadmin y crear_pastor; reglas de contraseña (mínimo 15 caracteres); bloqueo tras 5 intentos durante 15 minutos.
  • Comportamiento de los correos sin EMAIL_HOST (se muestran en la terminal) y del comando sembrar_demo.
  • Los comandos de la demostración se tomaron del README.md y del código; la demostración se usó en funcionamiento (puerto 8001) para las capturas del Manual de usuario.

Pendiente o no verificado

  • Despliegue en un servidor de producción (config.settings.production), dominio, HTTPS y copias de seguridad automáticas.
  • Envío real de correos por SMTP en la instalación limpia (se probó con los correos impresos en la terminal).
  • Instalación en Windows 10, Linux o macOS, y acceso desde otros equipos de la red local.
  • Requisitos mínimos de hardware.

Diferencias con la documentación existente

  • El README.md menciona 187 pruebas automáticas; al cierre de este manual hay 233.
  • El README.md habla de una «contraseña temporal» al crear usuarios; en la versión documentada el administrador asigna la contraseña al crear la cuenta y puede marcar que la persona la cambie al primer ingreso.
